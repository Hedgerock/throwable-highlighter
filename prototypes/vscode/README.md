# VS Code Prototype

Технический прототип интеграции Throwable Highlighter с VS Code.

## Назначение

Прототип проверяет возможность реализовать контракт Java-подсветки Throwable в VS Code без изменения стандартной Java-подсветки.

Первый этап проверил Semantic Tokens. Подход не позволил добавить собственные токены поверх используемой Java-поддержки.

Текущий этап проверяет editor decorations.

Прототип не является поддерживаемым пользовательским расширением.

## Поддерживаемые сценарии

Прототип выделяет известные стандартные типы:

- `Throwable`;
- `Exception`;
- `RuntimeException`;
- `IOException`;
- `IllegalArgumentException`;
- `IllegalStateException`.

Список является ограниченным каталогом известных стандартных типов и не описывает полную иерархию Throwable в JDK.

Каталог применяется только после подтверждения объявления Java-класса. Сопоставление выполняется по полному имени типа с
учётом пакета и внешних типов.

Остальные классы определяются проверкой прямого или транзитивного наследования от подтверждённого типа из каталога.

Простое имя символа и текст квалифицированной ссылки в месте использования не подтверждают принадлежность к Throwable.

Подсветка стандартных и пользовательских типов применяется в контекстах `CLASS`, `IMPORT`, `CATCH` и `THROWS`.

Транзитивный обход ограничен шестнадцатью переходами по иерархии классов. Недоступное определение, цикл или
превышение глубины сохраняют стандартную Java-подсветку.

Прототип не выполняет полное семантическое разрешение Java-кода и не является полным соответствием контракту Java-подсветки.

Известные ограничения описаны в [исследовании прототипа](../../docs/research/vscode-prototype.md#известные-ограничения).

Подсветка различает контексты:

- `CLASS` — объявление и обычная ссылка на тип;
- `IMPORT` — тип в явном импорте;
- `CATCH` — тип в параметре `catch`;
- `THROWS` — тип в списке `throws` метода или конструктора.

Для исключения комментариев, строковых литералов, символьных литералов и text blocks используется `JavaCodeMask`.

При поиске закрывающего разделителя text block учитывается экранирование кавычек и обратных слешей. Незавершённый text block
маскируется до конца документа.

Маскирование сохраняет длину исходного текста, позиции UTF-16 и переносы строк. Java-код после закрывающего разделителя
обрабатывается по существующим правилам.

## Запуск

1. Открыть папку как отдельную рабочую область VS Code.
2. Выполнить:
    
```powershell
npm install
npm run check
```

3. Запустить конфигурацию `Run Throwable Highlighter Prototype` клавишей F5.
4. В открытом Extension Development Host открыть Java-файл.

После изменения TypeScript-кода результаты обновляются командой `npm run compile` или работающим `npm run watch`.
Для загрузки обновлённого кода необходимо перезапустить Extension Development Host.

Перед коммитом выполняется `npm run check`.

## Автоматическая проверка

`npm run check` проверяет форматирование, собирает прототип и выполняет автоматические проверки.

`npm test` собирает и запускает все автоматические тесты прототипа.

`npm run test:build` проверяет учёт результатов сборки, хранение реестра, выборочную очистку, компиляцию и режим `watch`.

Интеграционные тесты используют настоящие TypeScript, `tsc-alias`, сборщик и Watch API. Тестовые проекты создаются во временных
каталогах. События изменения файлов и выполнение отложенных обработчиков задаются явно.

Проверки покрывают перемещение и удаление исходников, сохранение актуальных и посторонних файлов, независимость основной и
тестовой конфигураций, восстановление после ошибок и последовательное выполнение циклов.

Нативное наблюдение за файловой системой и завершение через Ctrl+C проверяются вручную.

`npm run test:hierarchy` отдельно проверяет `ThrowableHierarchyResolver` без запуска Extension Development Host и Definition
Provider.

Тесты `ThrowableHierarchyResolver` проверяют подтверждение класса по полному имени, прямое и транзитивное наследование,
нецелевые классы с известными простыми именами, отсутствие родителя, ограничение глубины, циклы и состояние `unavailable`.

Тесты `JavaClassNameReader` и `JavaClassDeclarationReader` проверяют чтение объявления класса, пакета, внешних типов и прямого
родителя.

Тесты `JavaDefinitionClassLocator` проверяют сопоставление определений классов и конструкторов с объявлением класса. Обычные
методы и позиции внутри тела конструктора не считаются определениями типа.

Тесты `JavaTypeDefinitionResolver` проверяют стандартные и пользовательские классы, совпадения имён других Java-символов,
цепочки наследования, вызовы конструкторов и обработку ответов Definition Provider.

Проверки также покрывают повторное разрешение недоступных определений, кэширование положительных и отрицательных результатов,
объединение запросов верхнего уровня, инвалидирование кэша и параллельный обход циклической иерархии.

Тесты `JavaThrowsClauseFinder` проверяют границы списков `throws`, методы и конструкторы, несколько типов, вложенные аргументы
аннотаций, квалифицированные имена и сохранение позиций ссылок на типы.

Тесты `JavaCatchClauseFinder` проверяют одиночный `catch`, multi-catch, модификатор `final`, аннотации с вложенными аргументами,
квалифицированные имена и незавершённые параметры. Имя параметра и ссылки внутри тела блока не включаются в диапазоны типов.

Тесты `JavaTypeReferenceRangeReader` проверяют исключение аннотаций, их аргументов и квалификаторов, ограничение чтения
заданным диапазоном и сохранение позиций ссылок после обработки `JavaCodeMask`.

Тесты `JavaImportClauseFinder` проверяют явные и многострочные импорты, комментарии между частями имени, вложенные типы,
wildcard imports и статические импорты.

Проверки покрывают разделение нескольких импортов на одной строке, сохранение позиций после обработки `JavaCodeMask`,
исключение import-подобного текста вне Java-кода и границы незавершённых объявлений.

Тесты `JavaCodeMask` проверяют завершённые и незавершённые text blocks, экранированные кавычки, чётные и нечётные
последовательности обратных слешей и сохранение Java-кода после закрывающего разделителя.

Проверки покрывают сохранение позиций UTF-16 и переносов строк LF, CRLF и CR. Обработка экранирования в обычных строковых
и символьных литералах проверяется отдельно.

Тесты `ThrowableHighlightingFinder` проверяют совместное определение `CLASS`, `IMPORT`, `CATCH` и `THROWS`, исключение
квалификаторов, wildcard imports и статических импортов из контекста `CLASS`, маскирование комментариев и литералов, сохранение
позиций UTF-16 и переносов строк.

Тесты `ThrowableDecorationController` проверяют применение подтверждённых результатов по четырём контекстам, очистку подсветки,
обработку отрицательных результатов и ошибок resolver, настройки цветов и наследование от `CLASS`.

Проверки покрывают неподдерживаемые документы, устаревшие асинхронные результаты, изменение конфигурации и завершение
жизненного цикла controller. Порядок завершения запросов не позволяет предыдущему обновлению заменить актуальный результат.

Тесты `ThrowableColorResolver` проверяют разрешение источников, наследование от `CLASS`, стандартную подсветку и сохранение
прежних правил цветов.

Тесты `ThrowableColorSettingParser` проверяют допустимые источники, форматы HEX, совместимость строковых значений и отклонение
некорректных данных.

Тесты `ThrowableColorConfigurationReader` проверяют разделение эффективных настроек и исходных значений `User` и `Workspace`.
Неполные настройки отдельных областей не проверяются как самостоятельная эффективная конфигурация.

Проверки controller дополнительно покрывают явные источники, обработку некорректной конфигурации и переключение источника
без изменения сохранённого собственного цвета.

Тесты `ThrowableColorSettingsDraft` проверяют учёт изменённых полей, сохранение собственного цвета при переключении источника,
отмену изменений и независимость черновиков `User` и `Workspace`.

Тесты `ThrowableColorSettingsMessageParser` проверяют структуру сообщений, допустимые контексты, источники и области настройки.
Неизвестные поля и операции с недоступной областью `Workspace` отклоняются.

Тесты `ThrowableColorSettingsResources` проверяют расположение ресурсов относительно URI расширения, загрузку шаблонов,
доступность файла стилей и повторную попытку после ошибки.

Тесты `ThrowableColorSettingsViewModelBuilder` проверяют выбор области, обработку недоступной `Workspace`, разделение исходных
и эффективных значений, сохранение частичных настроек и неизменность входного snapshot.

Тесты `ThrowableColorSettingsHtml` проверяют отображение контекстов, исходных значений области и эффективной конфигурации.
Проверки покрывают различие отсутствующего значения, `null` и пустой строки, обработку неподдерживаемых типов и сохранение
исходных значений при ошибке эффективной конфигурации.

Значения экранируются. Текст, похожий на места подстановки, не интерпретируется повторно. Неизвестные места подстановки
отклоняются. Подключение внешнего CSS и ограничения Content Security Policy проверяются отдельно.

Тесты `ThrowableColorSettingsPanel` проверяют создание и повторное открытие панели, обновление содержимого, освобождение
подписок и завершение жизненного цикла.

Проверки покрывают закрытие панели во время загрузки, устаревшие результаты и ошибки, получение актуальной конфигурации
после загрузки и повторную попытку после сбоя.

Исходные значения `User` проверяются отдельно от эффективных значений. Просмотр настроек не вызывает запись конфигурации.

`ThrowableColorSettingsTemplateContract.test.ts` проверяет соответствие подстановок каждого HTML-шаблона документированному
контракту и наличие непустых описаний.

Компоненты синтаксического разбора проверяются независимо от VS Code API. Для проверки finder и controller используется тестовая
реализация VS Code API. Ответы resolver в тестах controller задаются явно.

Работа с реальной Java-поддержкой и визуальное применение editor decorations проверяются отдельно в Extension Development Host.

## CI

Workflow [CI](../../.github/workflows/build.yml) запускается при push в `master` и для pull requests в `master`.

Отдельная job `vscode` выполняет проверки на Ubuntu с Node.js 22.

Тесты механизма локальной проверки запускаются из корня репозитория командой `node --test scripts/test/check-staged.test.cjs`.

Команды проверки прототипа выполняются из каталога `prototypes/vscode`. Зависимости устанавливаются командой `npm ci` по
зафиксированному lock-файлу. Команда `npm run check` проверяет форматирование, собирает прототип и запускает автоматические
тесты.

Подключение hook и ручной запуск проверки индекса описаны в документе [Локальная проверка подготовленного коммита](../../docs/local-checks.md).

CI не запускает Extension Development Host и не проверяет работу реальной Java-поддержки или визуальное применение decorations.

Сборка VSIX и публикация расширения VS Code в текущий workflow не входят.

## Импорты

Внутренние импорты используют алиас `@throwable-highlighter`, соответствующий каталогу `src`.

Путь указывает конкретный файл без расширения `.ts` и не зависит от расположения импортирующего модуля. Правило применяется
к исходному коду и тестам.

Импорты VS Code API, встроенных модулей Node.js и внешних зависимостей сохраняют стандартные имена.

Встроенные модули Node.js импортируются с префиксом `node:`.

Для сортировки используется следующий порядок групп:

1. Встроенные модули Node.js.
2. Внешние зависимости и VS Code API.
3. Внутренние модули с алиасом `@throwable-highlighter/`.
4. Относительные импорты.

Внутри каждой группы обычные импорты располагаются перед `import type`. Группы разделяются пустой строкой.

Порядок определяется в `.prettierrc.json` и применяется к исходному коду и тестам командами форматирования.

Сортировщик упорядочивает существующие импорты и не определяет необходимость `import type` по использованию символа.

После компиляции `tsc-alias` преобразует алиасы в относительные пути выходных JavaScript-файлов.

## Сборка и наблюдение

Для разработки прототипа требуется Node.js 22 или новее.

`npm run compile` собирает исходный код в `out` и преобразует пути импортов.

`npm run compile:test` собирает исходный код и тесты в `out-test` и преобразует пути импортов.

`npm run watch` выполняет первоначальную сборку и повторяет её при изменении программы TypeScript. Команда не перезапускает
Extension Development Host.

Сборкой управляет `TypeScriptBuildRunner`. Режим наблюдения использует `TypeScriptBuildWatcher` и `BuildCycleQueue`.

Каждый цикл формирует полный набор результатов текущей конфигурации. Циклы одного запущенного `watch` выполняются
последовательно. Изменения, поступившие во время активной сборки, объединяются в следующий запуск.

### Учёт и очистка результатов

В каждом выходном каталоге хранится отдельный `.build-output-registry.json`. Реестр является локальным результатом сборки
и не добавляется в Git.

В реестр включаются фактически записанные файлы. Ожидаемый набор результатов определяется программой TypeScript и параметрами
компиляции.

После успешной компиляции и преобразования импортов удаляются зарегистрированные файлы, которые отсутствуют в ожидаемом наборе.
Связанные source maps и оставшиеся пустые каталоги удаляются в пределах выходного каталога.

При ошибке компиляции или преобразования импортов очистка не выполняется. Учёт уже записанных файлов сохраняется для
последующих сборок. Ошибка сохранения реестра или очистки завершает соответствующий цикл с ошибкой.

Преобразование импортов применяется к результатам текущей компиляции. Остальные файлы сохраняются.

### Первоначальный учёт

Первый запуск регистрирует файлы, записанные текущей сборкой.

Существующие файлы не признаются результатами сборки автоматически. Ранее накопившиеся остатки проверяются отдельно и
удаляются вручную после подтверждения их принадлежности прежней структуре исходников.

Реализация соответствует [ADR-0017](../../docs/decisions/0017-selective-vscode-build-cleanup.md).

## Настройка цветов

Каждый контекст использует отдельное значение цвета и источник его получения.

Все настройки находятся в разделе `throwableHighlighter.prototype`.

| Контекст | Значение цвета | Источник цвета      |
|----------|----------------|---------------------|
| `CLASS`  | `classColor`   | `classColorSource`  |
| `IMPORT` | `importColor`  | `importColorSource` |
| `CATCH`  | `catchColor`   | `catchColorSource`  |
| `THROWS` | `throwsColor`  | `throwsColorSource` |

По умолчанию значения цветов равны пустой строке, источники — `null`.

### Источники цвета

Для `CLASS` доступны `custom` и `native`.

Для `IMPORT`, `CATCH` и `THROWS` дополнительно доступен `inherit`.

- `custom` использует собственное значение цвета соответствующего контекста;
- `inherit` использует результат разрешения цвета `CLASS`;
- `native` сохраняет стандартную Java-подсветку независимо от цвета `CLASS`.

Если `CLASS` сохраняет стандартную Java-подсветку, наследующие контексты также не получают foreground-decoration.

Расширение не вычисляет и не копирует стандартный цвет Java из активной темы.

Переключение источника не удаляет сохранённое собственное значение цвета.

### Совместимость

При отсутствии источника или значении `null` сохраняются прежние правила:

- пустое значение `classColor` сохраняет стандартную Java-подсветку;
- пустые значения `importColor`, `catchColor` и `throwsColor` наследуют цвет `CLASS`;
- непустое значение задаёт собственный цвет соответствующего контекста.

Строковые значения без явно выбранного источника не подвергаются новой HEX-проверке.

### Проверка значений

Источник `custom` требует цвет в формате `#RGB`, `#RGBA`, `#RRGGBB` или `#RRGGBBAA`.

Пробелы по краям строки не учитываются при проверке и применении цвета. Сохранённое значение не перезаписывается.

Цветовая настройка должна содержать строку. Неизвестный источник, недопустимое наследование `CLASS`, некорректный HEX для
`custom` или неправильный тип значения сохраняют стандартную Java-подсветку соответствующего контекста.

Если некорректна настройка `CLASS`, наследующие контексты также сохраняют стандартную Java-подсветку. Независимые собственные
цвета остальных контекстов продолжают применяться.

Некорректная конфигурация не изменяется автоматически.

### Области настройки

Настройки изменяются через Settings или Settings JSON в областях `User` и `Workspace`.

Приоритет конфигурации VS Code применяется отдельно к каждому ключу значения и источника цвета.

Если в `User` задан `catchColorSource: "native"`, изменение только `catchColor` в `Workspace` не включает собственный цвет.
Для изменения режима необходимо переопределить `catchColorSource` в соответствующей области.

Пример настройки:

```json
{
  "throwableHighlighter.prototype.classColor": "#4EC9B0",
  "throwableHighlighter.prototype.classColorSource": "custom",
  "throwableHighlighter.prototype.importColor": "#CE9178",
  "throwableHighlighter.prototype.importColorSource": "inherit",
  "throwableHighlighter.prototype.catchColor": "#C586C0",
  "throwableHighlighter.prototype.catchColorSource": "native",
  "throwableHighlighter.prototype.throwsColor": "#DCDCAA",
  "throwableHighlighter.prototype.throwsColorSource": "custom"
}
```

В примере `IMPORT` наследует цвет `CLASS`, `CATCH` сохраняет стандартную Java-подсветку, `THROWS` использует собственный
цвет.

Изменение настроек обновляет подсветку без перезапуска Extension Development Host.

### Панель просмотра цветов

Команда `Throwable Highlighter Prototype: Open Color Settings` открывает webview-панель просмотра настроек.

Панель показывает исходные значения области `User` отдельно от эффективной конфигурации контекстов `CLASS`, `IMPORT`, `CATCH` и
`THROWS`. Переключение области в панели пока не подключено.

Для каждого контекста отображаются исходный источник и значение цвета `User`, эффективный источник и эффективное сохранённое
значение цвета.

Строки исходных настроек выводятся в кавычках. `Not set in this scope` обозначает отсутствие настройки в области. Явный
`null` и пустая строка `""` отображаются отдельно. Неподдерживаемые типы значений выводятся как `Unsupported value`.

Эффективная конфигурация учитывает приоритеты VS Code. Сохранённое значение может не использоваться при выбранном источнике
`inherit` или `native`. Оно не является итоговым цветом после применения правил наследования.

Некорректная эффективная настройка отображается как ошибка. Исходные значения `User` остаются видимыми.

Повторный вызов команды показывает существующую панель. После закрытия команда создаёт новую панель.

Изменение настроек через Settings или Settings JSON обновляет панель без перезапуска Extension Development Host.

Панель работает только для чтения и не изменяет конфигурацию. Редактирование, выбор области сохранения и применение изменений
через панель пока недоступны. Кнопка `Apply` отключена.

Панель реализует часть [ADR-0014](../../docs/decisions/0014-interactive-vscode-color-settings.md).

HTML-шаблоны и CSS находятся в каталоге `webview/color-settings`. Ресурсы определяются относительно URI расширения.

CSS подключается отдельным локальным ресурсом. Доступ ограничен каталогом панели. Скрипты и сетевые ресурсы не используются.

Панель разделена на шапку, таблицу конфигурации, пояснения и блок действий, оформление использует цветовые и шрифтовые
CSS-переменные VS Code.

В узком окне таблица прокручивается по горизонтали внутри собственной области. Область доступна с клавиатуры и имеет видимую
рамку фокуса.

Ошибка загрузки отображается уведомлением. Повторный вызов команды позволяет повторить загрузку. Устаревшие результаты
и ошибки не изменяют актуальное содержимое панели и не вызывают уведомлений.

Разделение представления реализовано согласно [ADR-0015](../../docs/decisions/0015-separate-vscode-color-settings-presentation.md).

## Проверка

Для проверки используются fixtures из контракта Java-подсветки:

- `import-context.java` — типы в явных импортах используют `IMPORT`;
- `catch-context.java` — тип параметра `catch` использует `CATCH`, ссылка внутри тела блока использует `CLASS`;
- `multi-catch-context.java` — каждый тип использует `CATCH`;
- `syntax-preservation.java` — комментарии, модификаторы, ключевые слова и нецелевые элементы сохраняют стандартную
  Java-подсветку;
- `cross-file` — пользовательский прямой наследник в отдельном Java-файле использует контексты `CLASS`, `IMPORT` и `CATCH`;
- `transitive` — пользовательский транзитивный наследник требует последовательного определения `NestedException` и `BaseException`;
- `throws-context.java` — типы в списках `throws` методов и конструкторов используют `THROWS`, ссылка внутри тела метода
  использует `CLASS`.

При пустых значениях всех четырёх цветов и источниках `null` целевые типы сохраняют стандартную Java-подсветку.

Переключение источника между `custom`, `native` и `inherit` проверяется без перезапуска Extension Development Host.
Сохранённое собственное значение цвета не удаляется при переключении.

### Проверка панели просмотра цветов

В Extension Development Host проверяются следующие сценарии:

1. Команда открытия панели доступна без открытого Java-файла.
2. Панель показывает четыре контекста, исходные значения `User` и эффективную конфигурацию.
3. Повторный вызов команды показывает существующую панель.
4. После закрытия панель открывается повторно.
5. Изменение настроек через Settings или Settings JSON обновляет содержимое открытой панели.
6. Панель остаётся читаемой в светлой, тёмной и высококонтрастной темах.
7. Открытие и закрытие панели не изменяет конфигурацию.
8. Внешний CSS загружается, оформление сохраняется после повторного открытия панели и изменения настроек.
9. В узком окне горизонтальная прокрутка ограничивается областью таблицы.
10. Область таблицы получает фокус через Tab и прокручивается стрелками влево и вправо.
11. Переопределение настройки в `Workspace` отражается в эффективной конфигурации без изменения отображаемого значения `User`.
12. Отсутствующая настройка, явный `null` и пустая строка в исходных значениях отображаются различимо.
13. Ошибка эффективной конфигурации не скрывает исходные значения `User`.

Semantic Tokens provider успешно активируется в Extension Development Host.

Стандартная Java-поддержка VS Code сохраняет токен `class` для `RuntimeException`. Пользовательский токен `throwableClass` не
применяется.

Проверка Semantic Tokens завершена с отрицательным результатом.

## Результат editor decorations

Editor decorations применяются поверх стандартной Java-подсветки и не заменяют её.

Прототип различает контексты `CLASS`, `IMPORT`, `CATCH` и `THROWS`, поддерживает отдельные настройки цветов и наследование
цветов от `CLASS`.

Проверка editor decorations завершена успешно.

## Определение контекста IMPORT

`JavaImportClauseFinder` определяет диапазоны объявлений импорта и отдельно возвращает диапазон конечного имени типа для
завершённого явного нестатического импорта.

Компонент получает Java-код после обработки `JavaCodeMask` и не зависит от VS Code API.

Диапазон завершённого объявления начинается с ключевого слова `import` и заканчивается точкой с запятой. Переносы строк и
комментарии между частями имени не изменяют выбор контекста.

Имена пакетов и внешних типов не включаются в целевой диапазон. Wildcard imports и статические импорты не формируют целевой
диапазон.

Незавершённый импорт не формирует целевой диапазон. Его разбор не захватывает последующие объявления и тела блоков.

`ThrowableHighlightingFinder` использует диапазон объявления для исключения остальных идентификаторов импорта из обработки.
Квалификаторы и содержимое исключённых импортов не переходят в контекст `CLASS`.

После точки с запятой контекст определяется по существующим правилам.

Определение принадлежности типа к иерархии Throwable, настройки цветов и правила кэширования сохраняются.

Реализация соответствует [ADR-0012](../../docs/decisions/0012-separate-vscode-import-parsing.md).

---

## Определение контекстов CATCH и THROWS

`JavaCatchClauseFinder` определяет диапазоны имён типов в параметрах `catch`.

`JavaThrowsClauseFinder` определяет границы списков `throws` методов и конструкторов и диапазоны имён типов внутри них.

Компоненты получают Java-код после обработки `JavaCodeMask` и не зависят от VS Code API.

Границы конструкций определяются с учётом вложенных круглых скобок в аргументах аннотаций.

Оба компонента используют `JavaTypeReferenceRangeReader` для чтения ссылок в пределах найденной конструкции. Имена аннотаций,
их аргументы и квалификаторы не включаются в диапазоны типов.

В параметрах `catch` дополнительно исключаются модификатор `final` и имя параметра.

`ThrowableHighlightingFinder` назначает контекст найденным ссылкам. Принадлежность типа к иерархии Throwable проверяет
существующий `JavaTypeDefinitionResolver`.

Ссылки на типы внутри аргументов аннотаций и тел методов и блоков `catch` сохраняют контекст `CLASS`.

Реализация соответствует [ADR-0010](../../docs/decisions/0010-vscode-throws-throwable-highlighting.md) и
[ADR-0011](../../docs/decisions/0011-separate-vscode-context-parsing.md).

## Результат проверки Definition Provider

Прототип предоставляет команду `Throwable Highlighter Prototype: Inspect Definition`.

Команда вызывает документированную команду VS Code `vscode.executeDefinitionProvider` для символа под курсором и выводит
результат в Output Channel `Throwable Highlighter Prototype`.

Проверка подтвердила следующие сценарии:

- пользовательский `CustomException` разрешается в Java-файл рабочей области;
- `Throwable` разрешается в открываемый Java-документ виртуальной схемы `jdt://`;
- `RuntimeException` может не вернуть определение.

Отсутствие результата Definition Provider не считается ошибкой.

Definition Provider используется для разрешения ссылок на стандартные и пользовательские Java-классы.

Наличие ответа само по себе не подтверждает тип. Resolver проверяет найденное объявление класса.

При недоступном определении возвращается `unavailable`. Каталог известных типов не заменяет проверку объявления.

---

## Результат проверки JavaTypeDefinitionResolver

`JavaTypeDefinitionResolver` определяет принадлежность Java-символа к иерархии Throwable после подтверждения объявления класса.

Объявление класса в текущем документе проверяется непосредственно. Для ссылок используется `vscode.executeDefinitionProvider`
и проверка найденного объявления.

Подтверждённый класс считается целевым, если его полное имя входит в каталог известных стандартных типов либо проверенная
цепочка наследования достигает такого класса. Правило применяется к каждому родительскому типу.

Переменные, поля, параметры и обычные методы не считаются ссылками на тип из-за совпадения имени. Вызов конструктора обрабатывается
как использование соответствующего класса.

Недостаточные данные формируют `unavailable`, а не подтверждённый отрицательный результат.

Resolver подключён к editor decorations. Controller применяет подсветку только после положительного результата и игнорирует
устаревшее асинхронное обновление.

Реализация соответствует [ADR-0013](../../docs/decisions/0013-resolved-vscode-throwable-types.md).

---

## Результат проверки кэширования определения типов

Resolver кэширует в памяти Extension Host подтверждённые положительные и отрицательные результаты определения типов.

Ключ состоит из URI исходного документа, его версии и позиции потенциального типа.

Одновременные запросы верхнего уровня с одинаковым ключом используют общий незавершённый запрос. Рекурсивные обходы не
объединяют незавершённые запросы и сохраняют отдельный контекст посещённых объявлений.

Недоступные результаты не сохраняются и могут быть проверены повторно после готовности Java-поддержки.

Кэш очищается при изменении документов, создании, удалении или переименовании файлов и изменении состава рабочей области.
Результат запроса предыдущего поколения не заполняет актуальный кэш.

---

## Результат проверки транзитивного наследования

Fixture `transitive` подтверждает определение `NestedException`, который транзитивно наследует `RuntimeException` через
`BaseException`.

`NestedException` использует контексты `CLASS`, `IMPORT` и `CATCH`.

Изменение прямого родителя `BaseException` с `RuntimeException` на нецелевой тип снимает подсветку `NestedException`.
Возврат наследования от `RuntimeException` восстанавливает подсветку после инвалидирования кэша.

## Архитектура определения типов

`JavaTypeDefinitionResolver` является фасадом VS Code-интеграции. Он сохраняет публичный API для decoration controller и
Definition Probe, обращается к Definition Provider и владеет кэшем результатов.

`JavaClassDeclarationReader` выделяет ссылку на тип, разбирает заголовок Java-класса и определяет его прямого родителя.
Для исключения комментариев, строковых литералов, символьных литералов и text blocks он использует `JavaCodeMask`.

`JavaClassNameReader` определяет полное имя объявленного класса с учётом пакета и внешних типов.

`JavaDefinitionClassLocator` сопоставляет диапазон определения с классом или его конструктором по дереву символов документа.
Компонент работает с независимой моделью диапазонов и символов и не зависит от VS Code API.

`ThrowableHierarchyResolver` не зависит от VS Code API. Он обходит цепочку прямых родителей, ограничивает глубину, предотвращает
циклы и возвращает состояние `confirmed` либо `unavailable`.

Разделение реализовано согласно [ADR-0008](../../docs/decisions/0008-separate-vscode-hierarchy-resolution.md).

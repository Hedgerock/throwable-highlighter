# Выпуск новой версии

## Назначение

Документ описывает процесс выпуска новой версии Throwable Highlighter.

Релиз создаётся через GitHub Actions после публикации тега формата `v<major>.<minor>.<patch>`.

Пример тега:

```text
v1.2.0
```

---

## Версионирование

Проект использует Semantic Versioning.

- `PATCH` — исправление ошибки без новой пользовательской функциональности;
- `MINOR` — новая совместимая пользовательская функциональность;
- `MAJOR` — изменение, нарушающее обратную совместимость.

Изменения только в документации не требуют выпуска новой версии плагина.

---

## Подготовка релиза

Перед созданием тега необходимо:

1. Обновить `version` в `build.gradle.kts`.
2. Перенести изменения из раздела `Unreleased` в `CHANGELOG.md` в новый раздел с номером версии и датой.
3. Добавить краткие change notes для новой версии в `plugin.xml`.
4. Обновить `README.md`, описание плагина или документацию, если изменение влияет на поведение пользователя.
5. Убедиться, что CI для `master` завершился успешно.
6. Выполнить локальную проверку:

```text
test
verifyPlugin
buildPlugin
```

Для Windows можно использовать:

```powershell
.\gradlew.bat test verifyPlugin buildPlugin
```

---

## Создание релиза

После подготовки версии создается и отправляется тег:

```powershell
git tag -a v<version> -m "Release v<version>"
git push origin v<version>
```

Версия в теге должна совпадать со значением `version` в `build.gradle.kts`.

Например, для версии `1.2.0` используется тег `v1.2.0`.

---

## Release workflow

Workflow `.github/workflows/release.yml` запускается после push тега.

Он выполняет следующие действия:

1. Проверяет совпадение тега и версии плагина.
2. Запускает тесты.
3. Выполняет `verifyPlugin`.
4. Собирает ZIP-архив плагина.
5. Подписывает плагин.
6. Публикует плагин в JetBrains Marketplace.
7. Создаёт GitHub Release и прикрепляет ZIP-архив.

Для публикации используется GitHub Secrets:

- `PUBLISH_TOKEN`;
- `PRIVATE_KEY`;
- `PRIVATE_KEY_PASSWORD`;
- `CERTIFICATE_CHAIN`.

Значения секретов не хранятся в репозитории.

---

## Проверка после публикации

Успешное завершение GitHub Actions означает, что версия была отправлена в JetBrains Marketplace.

Одобрение Marketplace выполняется отдельно. До одобрения обновление может быть недоступно пользователям.

После одобрения необходимо:

1. Проверить доступность новой версии в JetBrains Marketplace.
2. Проверить установку плагина из IDE.
3. Проверить основной пользовательский сценарий изменения.
4. Обновить страницу Marketplace, скриншоты и дополнительные ссылки при необходимости.

---

## Ошибка выпуска

Если workflow завершается с ошибкой до публикации, необходимо определить причину ошибки.

Если ошибка является внешней или временной, workflow можно перезапустить через GitHub Actions.

Если для исправления требуется изменение кода, конфигурации или версии, необходимо создать новый коммит и выпустить
новую версию с новым тегом.

Если публикация в Marketplace уже могла начаться, номер версии нельзя использовать повторно до проверки
состояния версии в Marketplace.

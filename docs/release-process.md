# Выпуск новой версии

## Назначение

Документ описывает независимые выпуски Throwable Highlighter для IntelliJ Platform и VS Code. Каждая платформа использует
собственную версию и релизный тег.

| Платформа         | Формат тега                         | Workflow                                                   |
|-------------------|-------------------------------------|------------------------------------------------------------|
| IntelliJ Platform | `intellij-v<major>.<minor>.<patch>` | [Release](../.github/workflows/release.yml)                |
| VS Code           | `vscode-v<major>.<minor>.<patch>`   | [Release VS Code](../.github/workflows/release-vscode.yml) |

---

## Версионирование

Проект использует Semantic Versioning.

- `PATCH` — исправление ошибки без новой пользовательской функциональности;
- `MINOR` — новая совместимая пользовательская функциональность;
- `MAJOR` — изменение, нарушающее обратную совместимость.

## Выпуск IntelliJ Platform

Изменения только в документации не требуют выпуска новой версии плагина.

### Подготовка релиза

Перед созданием тега необходимо:

1. Обновить `version` в `extensions/intellij/build.gradle.kts`.
2. Перенести изменения из раздела `Unreleased` в `extensions/intellij/CHANGELOG.md` в новый раздел с номером версии и датой.
3. Добавить краткие change notes для новой версии в `extensions/intellij/src/main/resources/META-INF/plugin.xml`.
4. Обновить `README.md`, описание плагина или документацию, если изменение влияет на поведение пользователя.
5. Убедиться, что CI для `master` завершился успешно.
6. Выполнить локальную проверку:

```text
test
verifyPlugin
buildPlugin
```

Для Windows можно использовать:

```powershell
.\gradlew.bat -p extensions/intellij test verifyPlugin buildPlugin
```

Подключение проверок перед коммитом и ручной запуск проверки описаны в документе
[Локальная проверка подготовленного коммита](local-checks.md).

### Создание релиза

После подготовки версии создается и отправляется тег:

```powershell
git tag -a intellij-v1.5.1 -m "Release IntelliJ Platform 1.5.1"
git push origin intellij-v1.5.1
```

Версия в теге должна совпадать со значением `version` в `extensions/intellij/build.gradle.kts`.

### Release workflow

Workflow `.github/workflows/release.yml` запускается после push тега.

Он выполняет следующие действия:

1. Проверяет совпадение тега и версии плагина.
2. Запускает тесты.
3. Выполняет `verifyPlugin`.
4. Собирает ZIP-архив плагина.
5. Подписывает плагин.
6. Публикует плагин в JetBrains Marketplace.
7. Создаёт GitHub Release и прикрепляет ZIP-архив.

Для публикации используется GitHub Secrets:

- `PUBLISH_TOKEN`;
- `PRIVATE_KEY`;
- `PRIVATE_KEY_PASSWORD`;
- `CERTIFICATE_CHAIN`.

Значения секретов не хранятся в репозитории.

### Проверка после публикации

Успешное завершение GitHub Actions означает, что версия была отправлена в JetBrains Marketplace.

Одобрение Marketplace выполняется отдельно. До одобрения обновление может быть недоступно пользователям.

После одобрения необходимо:

1. Проверить доступность новой версии в JetBrains Marketplace.
2. Проверить установку плагина из IDE.
3. Проверить основной пользовательский сценарий изменения.
4. Обновить страницу Marketplace, скриншоты и дополнительные ссылки при необходимости.

### Ошибка выпуска

Если workflow завершается с ошибкой до публикации, необходимо определить причину ошибки.

Если ошибка является внешней или временной, workflow можно перезапустить через GitHub Actions.

Если для исправления требуется изменение кода, конфигурации или версии, необходимо создать новый коммит и выпустить
новую версию с новым тегом.

Если публикация в Marketplace уже могла начаться, номер версии нельзя использовать повторно до проверки
состояния версии в Marketplace.

## Выпуск VS Code

### Подготовка версии

Версия расширения хранится в `extensions/vscode/package.json`.
`extensions/vscode/package-lock.json` содержит ту же версию на верхнем уровне и в записи корневого пакета.

Пример обновления до `0.1.1` из корня репозитория:

```powershell
npm --prefix extensions/vscode version 0.1.1 --no-git-tag-version
```

Команда обновляет манифест и lock-файл. Коммит и релизный тег создаются отдельно.

### Ручная сборка кандидата

В GitHub Actions запускается **Release VS Code → Run workflow** на ветке с подготовленной версией. Workflow выполняет проверки
Node.js, браузерные проверки и тесты Extension Host. После успешного завершения задача **Build VSIX** собирает пакет и
сохраняет его в артефакте `throwable-highlighter-vsix`. Задача **Publish to Visual Studio Marketplace** получает статус
**Skipped**.

VSIX устанавливается в отдельном экземпляре VS Code для проверки установки и основного сценария подсветки. Контрольные замеры
выполняются на кандидате по [ADR-0031](decisions/0031-vscode-release-performance-budgets.md) и
[ADR-0034](decisions/0034-vscode-release-java-workspace-state.md).

### Публикация по тегу

После проверки кандидата тег создаётся на коммите, из которого он собран. Версия в теге совпадает с версией манифеста и
lock-файла.

```powershell
git tag -a vscode-v0.1.1 -m "Release VS Code 0.1.1"
git push origin vscode-v0.1.1
```

Workflow повторяет проверки и собирает VSIX из коммита тега. Задача публикации загружает VSIX из артефакта этого же запуска
и отправляет его в Visual Studio Marketplace через Trusted Publishing. Окружение `vscode-marketplace` разрешает релизные теги
VS Code. Задача публикации получает краткоживущие учётные данные через OIDC.

### Проверка после публикации

После появления новой версии в Visual Studio Marketplace проверяются версия в карточке, установка из **Extensions**, открытие
панели цветов и применение выбранного цвета в Java-проекте. Статический бейдж VS Code в корневом README обновляется после
появления версии в Marketplace.

При сбое публикации сначала проверяется, появилась ли версия в кабинете издателя. Если версия уже загружена, дальнейшие
действия определяются по её статусу в Marketplace. Если загрузка не состоялась и причина сбоя устранена в настройках окружения
или издателя, запускается повторная попытка для того же тега.

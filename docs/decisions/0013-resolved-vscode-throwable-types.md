# ADR-0013: Определение Throwable по разрешённому Java-типу в VS Code

## Статус

Принято.

---

## Контекст

Прототип VS Code использует `ThrowableTypeCatalog` как ограниченный fallback-набор стандартных типов Throwable.

Совпадение простого имени с каталогом формирует положительный результат без проверки объявления Java-класса. Правило
применяется к исходному кандидату и к родительским типам при обходе иерархии.

Совпадение имени переменной или нецелевого класса с именем из каталога создаёт ложную подсветку. Ложноположительный
результат также распространяется на наследников такого класса.

Контракт Java-подсветки определяет принадлежность к Throwable по разрешённому Java-типу, а не по простому имени.

Definition Provider может временно не вернуть определение существующего типа. Недоступное определение не подтверждает ни
принадлежность к Throwable, ни отсутствие наследования.

Прототипу требуется единое правило проверки стандартных и пользовательских типов без использования недокументированных API
Java-расширений VS Code.

---

## Решение

Простое имя Java-символа не является основанием для положительного результата определения Throwable.

`JavaTypeDefinitionResolver` подтверждает, что найденный символ является объявлением Java-класса либо ссылкой на Java-класс.

Объявление класса в текущем документе проверяется непосредственно. Для разрешения ссылок используется `vscode.executeDefinitionProvider`
и проверка найденного объявления.

Наличие результата Definition Provider само по себе не подтверждает принадлежность к Throwable.

Каталог известных стандартных типов используется только после подтверждения объявления класса. Сопоставление выполняется
по полному имени типа.

Полное имя учитывает пакет и внешние типы для вложенного класса. Простое имя или текст квалифицированной ссылки в месте
использования не заменяют проверку объявления.

Класс считается целевым, если его подтверждённое полное имя входит в каталог известных стандартных типов Throwable либо
проверенная цепочка его наследования достигает такого класса.

Правило применяется к исходному кандидату и к каждому родительскому типу. Совпадение простого имени родителя с каталогом
не завершает обход положительным результатом.

Переменные, параметры, поля и обычные методы не считаются ссылками на тип из-за совпадения имени. Вызов конструктора обрабатывается
как использование соответствующего Java-класса.

Если определение недоступно или данных недостаточно для подтверждения типа, возвращается `unavailable`. Стандартная Java-подсветка
сохраняется. Недоступный результат не сохраняется как подтверждённый отрицательный.

Подтверждённый нецелевой класс формирует отрицательный результат.

Разделение VS Code-интеграции и обхода иерархии сохраняется. Ограничение глубины и защита от циклов не изменяются.

Ключ кэша, объединение незавершённых запросов и правила инвалидирования сохраняются согласно ADR-0006. Подтверждённые
положительные и отрицательные результаты используют существующий механизм кэширования.

Решение уточняет правила применения каталога, принятые в ADR-0005, ADR-0006, ADR-0007 и ADR-0008. Остальные положения этих
решений сохраняются.

---

## Рассмотренные варианты

### Сохранить определение известных типов по простому имени

Вариант отклонён.

Простое имя не определяет вид Java-символа и не отличает стандартный тип Throwable от одноимённого нецелевого класса.

### Удалить проверку по имени только из JavaTypeDefinitionResolver

Вариант отклонён.

Проверки внутри `ThrowableHierarchyResolver` сохранят ложноположительные результаты при обработке исходного кандидата и
родительского типа.

### Считать недоступное определение подтверждённым нецелевым типом

Вариант отклонён.

Временная недоступность Java-поддержки не подтверждает отсутствие наследования Throwable. Кэширование такого результата
может препятствовать последующей корректной проверке.

---

## Последствия

Стандартные и пользовательские типы используют общее требование подтверждения Java-класса.

Каталог больше не подменяет разрешение символа при недоступном определении.

Первичная проверка стандартных типов может потребовать дополнительных обращений к Definition Provider. До получения
достаточных данных сохраняется стандартная Java-подсветка.

Автоматические проверки должны покрывать:

- подтверждённый стандартный тип Throwable;
- переменные, поля, параметры и методы с именами из каталога;
- нецелевой класс с именем известного стандартного исключения;
- вложенный нецелевой класс с совпадающим простым именем;
- наследника одноимённого нецелевого класса;
- пользовательский Throwable-класс, имя которого совпадает с именем из каталога;
- прямое и транзитивное наследование подтверждённого целевого типа;
- использование целевого типа при вызове конструктора;
- отсутствие положительного результата при наличии только текста квалифицированной ссылки;
- недоступное определение и недостаточные данные о типе;
- отсутствие кэширования недоступного результата;
- сохранение ограничения глубины и защиты от циклов.

Применение результата проверяется в контекстах `CLASS`, `IMPORT`, `CATCH` и `THROWS`.

Состояние реализации и известные ограничения обновляются в документации прототипа после проверки.

---

## Не входит в решение

- Расширение набора известных стандартных типов;
- Полное синтаксическое и семантическое разрешение Java-кода;
- Изменение глубины обхода и модели кэширования;
- Изменение синтаксического разбора контекстов подсветки;
- Добавление контекстов, настроек цветов и правил их наследования;
- Изменение IntelliJ-плагина;
- Создание общего исполняемого модуля для разных платформ;
- Публикация расширения VS Code.

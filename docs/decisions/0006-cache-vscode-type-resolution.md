# ADR-0006: Кэширование результатов определения типов в прототипе VS Code

## Статус

Принято.

---

## Контекст

`ThrowableDecorationController` повторно вызывает `JavaTypeDefinitionResolver` при каждом обновлении видимого Java-редактора.

Для пользовательского типа из другого Java-файла resolver использует `vscode.executeDefinitionProvider`. Запрос выполняется
асинхронно и зависит от готовности Java-поддержки VS Code.

После первого успешного определения типа повторный переход к уже открытому файлу снова вызывает Definition Provider. Это
создаёт заметную повторную задержку применения editor decorations.

[ADR-0005](0005-vscode-direct-throwable-inheritance.md) намеренно не включал кэширование результатов Definition Provider.
Текущая проверка межфайлового `ExternalException` подтверждает необходимость отдельного решения.

---

## Решение

`JavaTypeDefinitionResolver` хранит кэш подтверждённых результатов определения пользовательских типов в памяти Extension Host.

Ключ кэша состоит из URI исходного документа, его версии и позиции потенциального типа. Кэш не использует только простое
имя типа, так как одно имя может относиться к разным Java-типам.

Resolver также объединяет одновременные запросы для одинакового ключа, возникшие из нескольких асинхронных обновлений editor
decorations.

Результат считается подтверждённым, если Definition Provider вернул доступное определение и resolver смог проверить объявление типа.

Подтверждённые положительные и отрицательные результаты сохраняются в кэше.

Отсутствие результата Definition Provider, ошибка команды или недоступность документа определения не считаются подтверждённым
отрицательным результатом и не сохраняются в кэше.

Известные стандартные типы Throwable и пользовательские типы, объявленные в текущем документе с прямым наследованием, продолжают
определяться без Definition Provider.

Кэш очищается при изменении документа рабочей области, создании, удалении или переименовании файлов, а также при изменении
состава рабочей области.

Кэш существует только в течение работы Extension Host и не сохраняется на диск.

---

## Рассмотренные варианты

### Не использовать кэширование

Вариант отклонён.

Повторное обращение к Definition Provider при каждом переходе между редакторами создаёт заметную задержку повторного применения
подсветки.

### Кэшировать результат только по имени типа

Вариант отклонён.

Простое имя типа не является уникальным идентификатором Java-типа и может создать ложную подсветку.

### Кэшировать любой отрицательный результат

Вариант отклонён.

Во время запуска Java Language Server Definition Provider может временно не вернуть определение существующего пользовательского
типа. Сохранение такого результата не позволит повторной проверке применить подсветку.

### Сохранять кэш между запусками VS Code

Вариант отклонён.

Постоянный кэш требует отдельной модели валидности, формата хранения и очистки. Для технического прототипа достаточно кэша
Extension Host.

---

## Последствия

Повторная проверка уже определённого пользовательского типа не требует нового вызова Definition Provider, пока исходные
данные рабочей области не изменились.

Одновременные обновления одного редактора используют общий незавершённый запрос resolver.

Временная недоступность Java-поддержки не закрепляется в кэше. Ограниченные повторные обновления после активации продолжают
проверять такой тип.

`JavaTypeDefinitionResolver` получает ответственность за хранение, переиспользование и очистку результатов определения типов.

Потребуются проверки повторного открытия Java-файла, изменения объявления пользовательского исключения и временного отсутствия
Definition Provider.

---

## Не входит в решение

- Рекурсивная проверка транзитивного наследования;
- Кэширование между запусками VS Code;
- Кэширование результатов IntelliJ-плагина;
- Полное разрешение qualified names и пользовательских интерфейсов;
- Поддержка VS Code как пользовательской платформы;
- Создание Language Server Protocol сервера.

# ADR-0034: Уточнить состояние рабочей области для релизных замеров VS Code

## Статус

Принято.

---

## Контекст

[ADR-0031](0031-vscode-release-performance-budgets.md) требует подтвердить готовность Java перед контрольным прогоном.
Предрелизные замеры показали, что Working Set Java после `ServiceReady` зависит от состояния рабочей области и сборки JDT
при запуске.

Первый импорт новой рабочей области воспроизводит превышение бюджета памяти Java при включённом и отключённом Throwable Highlighter.
Повторный запуск Java в импортированной рабочей области может начинаться с существенно меньшего Working Set.

---

## Решение

Контрольный прогон `Usage100` выполняется в предварительно импортированной рабочей области. Перед прогоном завершаются
импорт и сборка проекта. Затем запускается новый Java-процесс с сохранённым состоянием рабочей области JDT.

После `ServiceReady` закрывается `ProbeException0001.java` и начинается окно контрольного замера. Для прогона сохраняются
журнал запуска JDT, PID Java и диапазон Working Set в первые 30 секунд с закрытыми Java-редакторами. Бюджеты и правило
повторной проверки применяются по ADR-0031. Высокий исходный Working Set учитывается в максимуме за окно измерения.

Первый импорт проверяется в новой рабочей области отдельным запуском. Для него фиксируются время до `ServiceReady`, максимальный
Working Set Java за первую минуту и Working Set в конце минуты.

---

## Последствия

Материалы выпуска содержат состояние рабочей области и исходный Working Set для каждого контрольного прогона. Замеры первого
импорта сохраняются в исследовании производительности.

---

## Не входит в решение

- Численный бюджет памяти Java для первого импорта.
- Изменение настроек JVM или сборки JDT.
- Оценка доли памяти Java, связанной с запросами Throwable Highlighter.

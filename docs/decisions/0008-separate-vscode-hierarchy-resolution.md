# ADR-0008: Разделение обхода иерархии и VS Code-интеграции в прототипе

## Статус

Принято.

---

## Контекст

`JavaTypeDefinitionResolver` определяет принадлежность Java-типа к иерархии Throwable.

После добавления транзитивного наследования компонент одновременно выполняет несколько задач:

- получает тип из документа VS Code;
- обращается к Definition Provider;
- открывает документы определений;
- разбирает заголовок Java-класса;
- обходит цепочку прямых родителей;
- ограничивает глубину обхода и предотвращает циклы;
- использует кэш результатов определения типов.

Такое объединение затрудняет изменение алгоритма обхода, улучшение разбора Java-заголовка и проверку граничных сценариев
без запуска Extension Development Host.

Прототип пока является единственной внешней платформенной реализацией. IntelliJ-плагин использует PSI и стандартную проверку
наследования IntelliJ Platform.

Проекту требуется разделить стабильный алгоритм обхода и VS Code-зависимую инфраструктуру без создания преждевременного
общего модуля для разных IDE.

---

## Решение

Алгоритм определения принадлежности типа к иерархии Throwable выделяется в отдельный компонент `ThrowableHierarchyResolver`.

`ThrowableHierarchyResolver` не зависит от API VS Code, документов, Definition Provider, кэша и разбора исходного текста.

Он отвечает за:

- обход прямых родителей;
- ограничение глубины;
- предотвращение циклов;
- обработку состояний `confirmed` и `unavailable`;
- применение `ThrowableTypeCatalog` как ограниченного fallback-набора типов.

Компонент получает сведения об объявлении класса и его прямом родителе через отдельный интерфейс источника иерархии.

VS Code-адаптер реализует этот интерфейс через `vscode.executeDefinitionProvider`, открытие документов и разбор Java-заголовка.

Разбор заголовка Java-класса выделяется в отдельный компонент `JavaClassDeclarationReader`. Он использует `JavaCodeMask` и
возвращает сведения об объявлении класса, его идентификаторе и прямом родителе.

`JavaTypeDefinitionResolver` сохраняет текущий публичный API для decoration controller и Definition Probe. После переработки
он становится фасадом VS Code-интеграции и владельцем кэша запросов.

Кэширование, объединение незавершённых запросов и правила инвалидирования сохраняются согласно [ADR-0006](0006-cache-vscode-type-resolution.md).
Ключ кэша, основанный на URI, версии документа и позиции типа, остаётся частью VS Code-адаптера.

Текущая подсветка, набор контекстов и поведение при недоступном определении не изменяются.

---

## Рассмотренные варианты

### Оставить всю логику в JavaTypeDefinitionResolver

Вариант отклонён.

Компонент уже содержит независимые обязанности. Дальнейшие изменения обхода или разбора будут требовать изменения VS Code-интеграции
и кэша одновременно.

### Создать общий модуль для IntelliJ Platform и VS Code

Вариант отклонён.

IntelliJ-плагин использует PSI и стандартные механизмы наследования платформы. Единственная реализация VS Code ещё не
подтверждает достаточную общность будущего межплатформенного API.

### Перенести кэш в ThrowableHierarchyResolver

Вариант отклонён.

Ключ кэша и условия инвалидирования зависят от URI, версии документа и событий рабочей области VS Code.

### Использовать внутренние API Java-расширений VS Code

Вариант отклонён.

Прототип сохраняет зависимость только от документированного API VS Code.

---

## Последствия

Алгоритм обхода можно проверять отдельно от Extension Development Host и Definition Provider.

Изменения Java-разбора локализуются в `JavaClassDeclarationReader`.

Изменения VS Code API, кэша и инвалидирования локализуются в адаптере и фасаде.

Количество исходных файлов и явных типов увеличивается.

Рефакторинг не добавляет новых пользовательских контекстов подсветки и не расширяет поддержку VS Code как пользовательской
платформы.

---

## Не входит в решение

- Создание общего модуля для IntelliJ Platform, VS Code, NetBeans или других IDE;
- Изменение алгоритма определения транзитивного наследования;
- Изменение глубины обхода;
- Расширение fallback-набора Throwable-типов;
- Кэширование между запусками VS Code;
- Полное семантическое разрешение Java-кода;
- Поддержка VS Code как пользовательской платформы;
- Создание Language Server Protocol сервера.

# ADR-0027: Ограничение параллельных обращений к Java-провайдерам VS Code

## Статус

Принято.

---

## Контекст

Планировщик объединяет последовательные запросы обновления подсветки. Количество обращений, запускаемых внутри обновления,
остаётся неограниченным.

Нагрузочный прогон с файлами на 10, 50 и 100 типов зафиксировал пики из 33, 153 и 303 одновременных вызовов Definition Provider.

Пик Document Symbol Provider составил 45 вызовов. Пики двух провайдеров достигнуты в разные моменты.

Оба вида обращений участвуют в определении Java-типа и используют общую Java-поддержку.

Очистка кэша делает результаты прежнего поколения неактуальными. Начатые команды могут продолжать выполняться после очистки.

---

## Решение

### Общий лимит

Выполнение команд Java-провайдеров выделяется в отдельный компонент ограничения параллелизма.

Один экземпляр компонента используется всеми обращениями JavaTypeDefinitionResolver, включая обращения из разных редакторов и
обновлений подсветки.

Общий лимит распространяется на команды:

- vscode.executeDefinitionProvider;
- vscode.executeDocumentSymbolProvider;

Суммарное количество начатых и незавершённых команд не превышает лимит.

Лимит является положительным целым числом и внутренним параметром. Его значение и результаты проверки фиксируются в
исследовании производительности.

Ограничение описывает вызовы команд со стороны resolver. Количество внутренних задач Java-сервера этим ограничением не
определяется.

### Выполнение и ожидание

При наличии свободного места команда запускается. Остальные обращения ожидают в общей очереди.

Актуальные обращения запускаются в порядке поступления.

Место занимается на время выполнения одной команды и освобождается при успешном завершении, отклонении Promise или синхронной
ошибке.

Рекурсивный обход иерархии не удерживает место между командами. Открытие документов и обработка полученных определений
выполняются вне занятого места.

Объединение запросов resolver с одинаковым ключом сохраняется. Ограничитель не вводит отдельное объединение команд.

Независимый обход иерархии сохраняет существующие интерфейсы. Управление очередью и актуальностью остаётся в интеграции
VS Code.

### Актуальность

Поколение кэша фиксируется при начале определения типа. Все обращения этого обхода сохраняют исходное поколение.

Перед запуском каждой команды проверяется актуальность её поколения.

При очистке кэша ожидающие команды прежних поколений снимаются с выполнения. Их Promise завершаются, resolver обрабатывает
снятые обращения как unavailable.

Снятое обращение не считается подтверждённым отрицательным результатом и не сохраняется в кэше.

Начатые команды прежнего поколения продолжают занимать места до завершения возвращённых Promise.

Смена поколения не обнуляет количество выполняющихся команд.

Завершение команды устаревшего обхода не запускает последующие команды этого обхода и не сохраняет его результаты в актуальном
поколении кэша.

Переключение редактора само по себе не меняет поколение кэша. Переиспользование ожидающих результатов и проверки актуальности
применения подсветки сохраняются.

### Освобождение ресурсов

Освобождение resolver закрывает ограничитель и снимает все ожидающие команды. Promise снятых обращений завершаются.

Новые обращения после освобождения не запускаются и не добавляются в очередь.

Начатые команды завершаются с освобождением занятых мест. Их завершение не возобновляет обработку очереди и не запускает
дальнейший обход.

Повторное освобождение не изменяет состояние.

### Измерения

Счётчики Definition Provider и Document Symbol Provider учитывают команды после получения свободного места.

Ожидание в очереди не считается выполняющимся вызовом провайдера.

Локальные измерения ресурсов дополняются количеством ожидающих команд, общим количеством выполняющихся команд и их пиковыми
значениями.

Карта ожидающих результатов resolver и очередь команд учитываются отдельно.

---

## Рассмотренные варианты

### Ограничить только Definition Provider

Вариант отклонён.

Document Symbol Provider также участвует в определении типов. Измерения подтверждают параллельные обращения к этому провайдеру.

### Использовать независимый лимит для каждого провайдера

Вариант отклонён.

Раздельные лимиты допускают одновременное выполнение команд двух видов с суммарным количеством выше выбранной общей границы.

---

## Последствия

Resolver получает отдельный компонент управления выполнением команд и освобождает его вместе с собственным состоянием.

Обращения получают дополнительное время ожидания при занятом лимите. Влияние ожидания проверяется повторными нагрузочными
прогонами.

Автоматические проверки покрывают:

- соблюдение общего лимита для двух видов команд;
- совместное использование лимита несколькими обращениями resolver;
- порядок запуска ожидающих команд;
- освобождение места при успешном завершении и ошибках;
- рекурсивное определение типа при лимите 1;
- снятие ожидающих команд при смене поколения;
- сохранения учёта начатых команд прежнего поколения;
- отсутствие продолжения устаревшего обхода;
- завершение ожидающих Promise при освобождении;
- отсутствие новых команд после освобождения;
- сохранение объединения запросов и защиты от циклов;
- раздельный учёт ожидающих и выполняющихся команд.

После интеграции повторяется прогон со 100 типами и повторными открытиями файлов. Сравниваются параллелизм, ожидание, время
применения подсветки и память обоих процессов.

---

## Не входит в решение

- Ограничение размера кэша и вытеснение записей;
- Численное ограничение длины очереди;
- Отмена уже запущенных команд Java-поддержки;
- Таймауты команд;
- Прямые диагностические вызовы DefinitionProbe;
- Пользовательская настройка лимита;
- Пользовательская индикация ожидания;
- Численные бюджеты общей памяти процессов.

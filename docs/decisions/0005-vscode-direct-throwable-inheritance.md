# ADR-0005: Определение прямых наследников Throwable в прототипе VS Code

## Статус

Принято.

---

## Контекст

Текущий прототип VS Code использует editor decorations и определяет целевые типы по известным простым именам.

Такой подход поддерживает ограниченный набор стандартных типов Throwable, но не определяет пользовательские исключения.

Проверка `vscode.executeDefinitionProvider` подтвердила, что прототип может получить определение пользовательского `CustomException`
в Java-файле рабочей области и открыть определение `Throwable` из виртуального Java-документа `jdt://`.

Definition Provider может не вернуть определение даже для стандартного Java-типа. Отсутствие результата является допустимым
и не должно приводить к ошибке или изменению стандартной Java-подсветки.

Прототипу требуется минимальный способ подтвердить пользовательский тип как наследника Throwable без использования
недокументированных API Java-расширений VS Code.

---

## Решение

Прототип VS Code вводит отдельный `JavaTypeDefinitionResolver`.

Resolver получает потенциальный Java-тип, вызывает `vscode.executeDefinitionProvider` и проверяет документ найденного
определения.

Пользовательский тип считается целевым, если его объявление содержит прямое наследование от известного типа Throwable.

Известные стандартные типы Throwable продолжают определяться по известным именам и не требуют вызова Definition Provider.

Если Definition Provider не вернул определение, документ определения недоступен или прямое наследование не подтверждено,
тип не считается целевым.

Текущая реализация decorations применяет подсветку только после положительного результата resolver для пользовательского
типа.

---

## Рассмотренные варианты

### Определение пользовательских типов только по имени

Вариант отклонён.

Имя пользовательского типа не подтверждает его принадлежность к иерархии Throwable и создаёт ложную подсветку.

### Использование недокументированных API Java-расширений VS Code

Вариант отклонён.

Прототип не должен зависеть от внутренней реализации Java-расширения или от API без гарантий совместимости.

### Рекурсивная проверка всей иерархии наследования

Вариант отложен.

Рекурсивная проверка требует отдельного решения о кэшировании, обработке циклов, ограничении глубины и обновлении результатов
при изменении документов.

---

## Последствия

Прототип получает минимальную поддержку пользовательских классов, которые напрямую наследуют известный тип Throwable.

Логика определения пользовательских типов становится асинхронной и отделяется от поиска синтаксических контекстов `CLASS`,
`IMPORT` и `CATCH`.

Отсутствие ответа Definition Provider сохраняет стандартную Java-подсветку и не создаёт ошибок в Output Channel.

Проверка потребует сценариев для прямого пользовательского наследника, нецелевого класса и недоступного определения.


---

## Не входит в решение

- Рекурсивная проверка транзитивного наследования;
- Кэширование результатов Definition Provider;
- Поддержка пользовательских интерфейсов и других форм Java-типов;
- Полное разрешение импортов и qualified names;
- Изменение правил подсветки IntelliJ-плагина;
- Поддержка VS Code как пользовательской платформы;
- Создание Language Server Protocol сервера.

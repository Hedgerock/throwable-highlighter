# ADR-0024: Планирование обновлений подсветки VS Code

## Статус

Принято.

---

## Контекст

Каждый вызов refresh запускает определение типов для кандидатов во всех видимых редакторах.

Последовательные события создают перекрывающиеся асинхронные обновления.
Проверка поколения блокирует применение устаревшего результата после завершения вычислений.

Контролируемый прогон с тысячей кандидатов и двадцатью запросами обновления
зафиксировал двадцать тысяч вызовов управляемого resolver.
Пиковое количество незавершённых вызовов составило три тысячи.
В редакторе применён один актуальный результат.

Измерения подтверждают повторную работу, но не определяют оптимальные задержки
и ограничения настоящей Java-поддержки.

Для объединения последовательных событий требуется отдельное планирование запусков.

---

## Решение

Планирование обновлений выделяется в отдельный компонент.

Планировщик управляет моментом запуска.
Определение типов, проверка актуальности и применение подсветки остаются
обязанностями существующих компонентов.

### Отложенные запросы

События изменения документов, файлов и состава рабочей области
формируют отложенный запрос обновления.

Последовательные запросы объединяются по правилу debounce:
запуск выполняется после заданного периода без новых отложенных запросов.

Максимальное ожидание отсчитывается от первого запроса ожидающей серии.
Последующие запросы не переносят эту границу.

Планировщик хранит один ожидающий запуск.
Отдельные задания для каждого события не накапливаются.

При запуске используется актуальный набор видимых редакторов.
Снимки документов и кандидатов не создаются на этапе ожидания.

### Срочные запросы

Первоначальное обновление, подтверждение готовности Java-поддержки,
смена активного или видимых редакторов и изменение цветовой конфигурации
формируют срочный запрос.

Срочный запрос выполняется при ближайшей возможности
без ожидания периода debounce.

Он объединяется с накопленным отложенным запросом.
Прежние таймеры ожидания отменяются.

Повторные срочные запросы до выполнения ожидающего запуска объединяются.

Новый отложенный запрос включается в уже запланированный срочный запуск.
Срочность и момент этого запуска сохраняются.

### Инвалидирование

Очистка кэша выполняется при получении соответствующего события
согласно ADR-0006 и ADR-0022.

Получение нового запроса сразу делает прежнее вычисление неактуальным.
Инвалидирование не откладывается до запуска планировщика.

Проверки поколения, версии документа, принадлежности редактора документу
и состояния dispose сохраняются.

Правила подтверждения Java-типов и выбора контекстов подсветки сохраняются.

### Параметры и выполняющаяся работа

Задержка debounce и максимальное ожидание являются внутренними параметрами.

Выбор значений и результаты их проверки фиксируются
в исследовании производительности.

Параметры проверяются повторными контролируемыми прогонами
и запуском в Extension Host.

Заданная задержка управляемого resolver не определяет
бюджет обновления расширения.

Планирование ожидающего запуска не требует завершения
предыдущего асинхронного вычисления.

Ограничение ожидающего запуска не считается ограничением
количества выполняющихся обращений к resolver.

### Освобождение ресурсов

Dispose отменяет ожидающие запуски и освобождает таймеры планировщика.

Новые запросы после dispose игнорируются.

Завершение ранее начатых вычислений не применяет подсветку
и не создаёт новых запланированных обновлений.

---

## Рассмотренные варианты

### Сохранить запуск для каждого события

Вариант отклонён.

Контролируемые измерения подтверждают повторную работу,
результаты которой не применяются.

### Использовать debounce без максимального ожидания

Вариант отклонён.

Непрерывная последовательность событий может откладывать запуск
до завершения всей серии.

### Использовать throttle с завершающим запуском

Вариант отклонён.

Приоритет отдан запуску после короткой паузы в редактировании.
Максимальное ожидание ограничивает перенос запуска при продолжительной серии.

### Выполнять все вычисления через общую последовательную очередь

Вариант отклонён.

Продолжительное вычисление задерживает последующие обновления
и работу остальных редакторов.

Ограничения выполняющихся обращений требуют отдельного решения.

---

## Последствия

Прототип получает отдельный компонент планирования.

Обработчики событий разделяют немедленное инвалидирование
и запрос запуска вычислений.

Отложенное обновление получает дополнительную задержку.
Её влияние проверяется вместе с сокращением повторных вызовов resolver.

Автоматические проверки покрывают:

- объединение отложенных запросов;
- запуск после завершения короткой серии;
- максимальное ожидание при непрерывных запросах;
- срочный запуск и отмену прежних таймеров;
- немедленное инвалидирование устаревших результатов;
- получение актуального набора редакторов при запуске;
- освобождение планировщика до и во время вычислений;
- сохранение срочного запуска при последующих отложенных запросах;
- отсутствие запусков и применения результатов после dispose.

Время в проверках планировщика управляется явно.

После интеграции повторяются контролируемые измерения
одиночного обновления, серии запросов, двух редакторов и dispose.

Измерения настоящей Java-поддержки, памяти и ограничения выполняющейся работы
сохраняются в обязательном предрелизном плане.

---

## Не входит в решение

- Ограничение параллельных обращений к resolver и Definition Provider;
- Отмена уже вызванных команд Java-поддержки;
- Таймауты отдельных обращений;
- Ограничения размера кэшей;
- Численные бюджеты времени и памяти;
- Пользовательские настройки планирования;
- Локальная диагностика состояния расширения.

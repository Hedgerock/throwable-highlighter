# ADR-0023: Интеграционные проверки в Extension Host VS Code

## Статус

Принято.

---

## Контекст

Компонентные тесты прототипа используют подмену VS Code API.

Браузерные проверки выполняют представление панели при заданном обмене сообщениями.

Эти проверки не подтверждают работу расширения с настоящим VS Code API,
Java-сервером и конфигурацией редактора.

Восстановление подсветки при холодном старте проверено вручную.
Повторяемая автоматическая проверка интеграции требуется перед публичным выпуском.

---

## Решение

Прототип получает отдельный набор интеграционных тестов,
которые выполняются в настоящем Extension Host VS Code.

Для запуска используется `@vscode/test-cli`.
Сценарии выполняются средствами Mocha.

### Разделение проверок

Интеграционные тесты используют настоящий модуль `vscode`.

Подмена `test/support/vscode.ts` и переназначение методов VS Code API
в этих сценариях не применяются.

Тесты получают отдельную конфигурацию TypeScript и каталог результатов сборки.
Они не включаются в обычный прогон компонентных тестов.

Сборка использует существующий механизм учёта и очистки выходных файлов.

Для проверки компонентов используются их существующие интерфейсы.
Производственный код не получает команд и экспортов исключительно для тестирования.

### Тестовое окружение

Запуск использует отдельные каталоги пользовательских данных,
установленных расширений и временную рабочую область.

Пользовательская конфигурация редактора и исходные fixtures не изменяются.

Версии VS Code и `redhat.java` фиксируются в конфигурации запуска.
Требования к Java runtime фиксируются в настройке тестового окружения.

Совместимость выбранного сочетания подтверждается запуском проверок.

Успешный прогон не подтверждает поддержку всех версий,
допускаемых текущим `engines.vscode`.

Java-поддержка запускается в стандартном режиме.
Готовность сервера определяется через `serverReady()` согласно ADR-0022.

Ожидание готовности и результатов Java-поддержки ограничивается временем.
Условием продолжения является наблюдаемый результат,
а не истечение произвольной задержки.

Отсутствие необходимого расширения, ошибка запуска и превышение времени
ожидания завершают проверку с ошибкой.

### Проверяемое поведение

Начальный набор покрывает:

- активацию расширения и регистрацию пользовательских команд;
- получение определений стандартных Java-типов;
- определение пользовательских Throwable при прямом и транзитивном
  межфайловом наследовании;
- отсутствие положительного результата для нецелевого класса;
- получение диапазонов и контекстов через основной компонент поиска подсветки;
- запись, чтение и удаление настроек в областях `User` и `Workspace`
  через существующие компоненты работы с конфигурацией.

Для Java-сценариев используются существующие fixtures.
При необходимости они копируются в подготовленную тестовую рабочую область.

Проверка диапазонов и настроек не считается подтверждением
визуального применения decorations редактором.

### Запуск проверок

Интеграционные тесты запускаются отдельной локальной командой
и отдельной job GitHub Actions.

Существующие компонентные и браузерные проверки сохраняются.

Состав локального `pre-commit` не изменяется.

При ошибке сохраняются сведения о версиях окружения,
вывод тестов и доступные журналы запуска.

---

## Рассмотренные варианты

### Сохранить только ручные проверки Extension Development Host

Вариант отклонён.

Ручная проверка зависит от состояния установленного редактора
и не обеспечивает повторяемую проверку интеграции в CI.

### Использовать подмену VS Code API в новом наборе

Вариант отклонён.

Такой набор повторяет ограничения существующих компонентных тестов
и не проверяет взаимодействие с настоящей Java-поддержкой.

---

## Последствия

Прототип получает дополнительные зависимости разработки
и отдельное окружение интеграционных проверок.

Первый запуск требует загрузки VS Code и Java-расширения.

Продолжительность проверок зависит от запуска редактора
и подготовки Java-проекта.

Результаты компонентных, браузерных и интеграционных проверок
оцениваются с учётом границ каждого набора.

Ручная проверка визуальной подсветки при холодном старте сохраняется.

Порядок запуска и разбора ошибок описывается в документации прототипа
после реализации.

---

## Не входит в решение

- Автоматизация всего интерфейса VS Code;
- Автоматическая проверка визуального применения decorations;
- Проверка установки VSIX;
- Определение публичного диапазона совместимости;
- Изменение постоянных идентификаторов и процесса выпуска;
- Изменение поведения подсветки и IntelliJ-плагина.

# Технический прототип VS Code

## Назначение

Документ определяет границы технического прототипа Throwable Highlighter для VS Code.

Прототип проверяет возможность реализовать контракт Java-подсветки без изменения стандартной Java-подсветки VS Code.

Прототип не является поддерживаемым пользовательским расширением.

---

## Проверяемые гипотезы

VS Code позволяет выделять диапазоны типов `Throwable` и его наследников в Java-коде без изменения подсветки нецелевых
элементов.

Подсветка прототипа может работать совместно с используемой Java-поддержкой VS Code.

Платформа позволяет предоставить отдельную настройку визуального стиля для контекстов `CLASS`, `IMPORT`, `CATCH` и `THROWS` либо
эквивалентное поведение.

---

## Подходы к проверке

Прототип проверяет возможность использовать Semantic Tokens.

Semantic Tokens не должны заменять или ухудшать стандартную Java-подсветку.

Если Semantic Tokens не позволяют сохранить стандартную Java-подсветку, прототип проверяет возможность
использования editor decorations.

Editor decorations не заменяют стандартную токенизацию, но требуют отдельного определения типов `Throwable`.

Прототип не использует недокументированные API Java-расширений VS Code.

---

## Сценарии проверки

Прототип использует fixtures из [контракта Java-подсветки](../specification/java-highlighting-contract.md).

На первом этапе проверяются:

- явный импорт `Throwable` и его наследника;
- обычная ссылка на `RuntimeException`;
- тип в параметре `catch`;
- ссылка на `RuntimeException` внутри тела `catch`;
- сохранение подсветки модификаторов, комментариев и ключевых слов.

Прототип реализует контекст `THROWS` для типов в списках `throws` методов и конструкторов.

Для проверки используется fixture `throws-context.java`. Каждый тип списка обрабатывается отдельно. Ссылки на типы внутри
тела метода сохраняют контекст `CLASS`.

Реализация определена [ADR-0010](../decisions/0010-vscode-throws-throwable-highlighting.md).

Проверка пользовательских исключений с прямым и транзитивным наследованием выполнена через `JavaTypeDefinitionResolver`.

`JavaTypeDefinitionResolver` подключён к editor decorations и подтверждает пользовательский тип перед применением подсветки.

---

## Критерии успеха

Прототип считается успешным, если:

- подсветка применяется только к имени целевого типа;
- контексты `CLASS`, `IMPORT`, `CATCH` и `THROWS` различаются;
- нецелевая Java-подсветка сохраняется;
- прототип работает совместно с используемой Java-поддержкой VS Code;
- настройки цветов не требуют изменения темы целиком;
- реализация не использует недокументированные API.

---

## Не входит в прототип

- Публикация расширения в Visual Studio Marketplace;
- Поддержка NetBeans, Eclipse IDE и других платформ;
- Полное покрытие всех fixtures;
- Создание общего исполняемого модуля;
- Создание Language Server Protocol сервера;
- Перенос существующего IntelliJ-плагина.

---

## Результат проверки Semantic Tokens

Semantic Tokens provider прототипа успешно активируется в Extension Development Host.

При открытии Java-файла стандартная Java-поддержка VS Code сохраняет семантический токен `class` для `RuntimeException`.
Пользовательский токен `throwableClass` не применяется.

Подход с Semantic Tokens не позволяет добавить подсветку Throwable поверх используемой Java-поддержки без риска замены или
потери стандартной подсветки Java.

Проверка Semantic Tokens считается завершённой с отрицательным результатом.

---

## Результат проверки editor decorations

Editor decorations применяются поверх стандартной Java-подсветки и не заменяют её.

Прототип выделяет известные стандартные типы Throwable в контекстах `CLASS`, `IMPORT`, `CATCH` и `THROWS`.

Прототип также выделяет пользовательский класс с прямым наследованием от известного типа Throwable.

Прототип предоставляет отдельные значения и источники цветов для каждого контекста.

Для `CLASS` доступны собственный цвет и стандартная Java-подсветка. Для `IMPORT`, `CATCH` и `THROWS` дополнительно доступно
наследование результата разрешения цвета `CLASS`.

При отсутствии источника или значении `null` сохраняются прежние правила обработки пустых и непустых цветовых строк.

Для исключения комментариев, строковых литералов, символьных литералов и text blocks используется `JavaCodeMask`.

Проверка editor decorations считается успешной.

---

## Результат проверки Definition Provider

Прототип вызывает документированную команду VS Code `vscode.executeDefinitionProvider` для Java-символа под курсором.

Проверка пользовательского `CustomException` вернула определение в Java-файле рабочей области.

Проверка `Throwable` вернула определение в Java-документе виртуальной схемы `jdt://`. VS Code открыл документ как Java-файл.

Проверка `RuntimeException` не вернула определение. Отсутствие результата Definition Provider является допустимым
результатом и не подтверждает принадлежность типа к иерархии Throwable.

Проверка подтвердила возможность использовать Definition Provider в `JavaTypeDefinitionResolver` для определения пользовательских
Java-типов.

Ответ Definition Provider для стандартного Java-типа может отличаться между проверками. Стандартные и пользовательские ссылки
требуют проверки найденного объявления. Каталог известных типов не используется при недоступном определении.

---

## Состояние прототипа

Способ наложения подсветки на Java-код в VS Code определён: прототип использует editor decorations.

`JavaTypeDefinitionResolver` подключён к decoration controller и подтверждает объявление класса перед определением
принадлежности к Throwable.

Каталог известных стандартных типов применяется по полному имени подтверждённого класса. Для остальных классов проверяется
цепочка прямых родителей с ограничением в шестнадцать переходов и защитой от циклов.

Простое имя символа не формирует положительный результат. Правило распространяется на исходного кандидата и родительские
типы согласно [ADR-0013](../decisions/0013-resolved-vscode-throwable-types.md).

`JavaClassDeclarationReader` разбирает объявление и прямого родителя класса. `JavaClassNameReader` определяет полное имя с
учётом пакета и внешних типов. `JavaDefinitionClassLocator` сопоставляет определения классов и конструкторов с объявлением
класса по дереву символов документа.

`ThrowableHierarchyResolver` выполняет независимый от VS Code API обход иерархии. Фасад владеет кэшем и обращается к Definition
Provider.

`ThrowableDecorationController` применяет подтверждённые результаты resolver в контекстах `CLASS`, `IMPORT`, `CATCH` и `THROWS`.

Асинхронный результат не применяется, если началось более новое обновление, изменился документ или его версия, документ
перестал поддерживаться либо был вызван `dispose()`.

При изменении конфигурации активный controller освобождает прежние типы decorations, создаёт новые и запускает обновление
подсветки. Результаты предыдущего обновления не применяются.

`dispose()` освобождает типы decorations однократно. Последующие обновления не создают новые типы и не применяют подсветку.

Определение контекстов, применение результатов, настройки цветов и жизненный цикл controller покрыты компонентными тестами.
Проверка controller использует тестовую реализацию VS Code API и контролируемые ответы resolver.

После активации controller выполняет ограниченные повторные проверки, чтобы дождаться готовности Java-поддержки для
межфайлового разрешения типов.

Resolver кэширует в памяти Extension Host подтверждённые положительные и отрицательные результаты определения типов.

Ключ состоит из URI исходного документа, его версии и позиции потенциального типа.

Одновременные запросы верхнего уровня с одинаковым ключом используют общий незавершённый запрос. Рекурсивные обходы не
объединяют незавершённые запросы и сохраняют отдельный контекст посещённых объявлений.

Недоступные результаты не сохраняются и могут быть проверены повторно после готовности Java-поддержки.

Кэш очищается при изменении документов, создании, удалении или переименовании файлов и изменении состава рабочей области.
Результат запроса предыдущего поколения не заполняет актуальный кэш.

`JavaCatchClauseFinder` определяет диапазоны имён типов в параметрах `catch`. `JavaThrowsClauseFinder` определяет границы
списков `throws` и диапазоны имён типов внутри них.

Компоненты работают с результатом `JavaCodeMask`, учитывают вложенные аргументы аннотаций и не зависят от VS Code API.

Обработка аннотаций и квалифицированных ссылок выделена в общий `JavaTypeReferenceRangeReader`.

`ThrowableHighlightingFinder` использует найденные диапазоны для выбора контекстов `CATCH` и `THROWS`. Определение принадлежности
типа к иерархии Throwable и правила кэширования остаются общими для всех контекстов.

Разделение реализовано согласно [ADR-0011](../decisions/0011-separate-vscode-context-parsing.md).

Разбор объявлений импорта выделен в `JavaImportClauseFinder`. Компонент определяет диапазон объявления и конечное имя типа в
завершённом явном нестатическом импорте.

`ThrowableHighlightingFinder` использует найденные диапазоны для выбора контекста `IMPORT` и исключения остальных идентификаторов
импорта. Квалификаторы, wildcard imports и статические импорты не переходят в контекст `CLASS`.

Границы импорта не зависят от расположения частей имени по строкам. Код после завершённого объявления обрабатывается по
существующим правилам выбора контекста.

Разделение реализовано согласно [ADR-0012](../decisions/0012-separate-vscode-import-parsing.md).

`JavaCodeMask` учитывает экранирование кавычек и обратных слешей при определении границ text blocks. Содержимое блока
исключается из поиска типов и определения контекстов подсветки. Код после закрывающего разделителя остаётся доступным для
обработки.

Границы завершённых и незавершённых блоков, чётные и нечётные последовательности обратных слешей, сохранение позиций UTF-16
и переносов строк покрыты регрессионными тестами.

Прототип не является пользовательским расширением и не подтверждает поддержку VS Code как пользовательской платформы проекта.

Поддержка VS Code как пользовательской платформы принимается отдельным ADR.

## Модель настройки цветов

Значение собственного цвета и источник его получения представлены отдельно в `ThrowableColorSettings`.

`ThrowableColorSettingParser` проверяет данные из конфигурации. Явный источник `custom` требует допустимый HEX. Совместимость
прежних строковых значений сохраняется при отсутствии источника или значении `null`.

`ThrowableColorSettingsParser` выполняет общий разбор четырёх контекстов для сохранённой конфигурации и предпросмотра.
Правила проверки отдельного значения остаются в `ThrowableColorSettingParser`.

`ThrowableColorConfigurationReader` получает эффективные значения через `get`, а значения по умолчанию и областей `User`
и `Workspace` — через `inspect`.

Эффективные настройки проходят разбор. Значения отдельных областей возвращаются без подстановки эффективных значений: область
может содержать только часть настроек.

Приоритеты отдельных ключей определяет VS Code. Reader не вводит собственное объединение настроек контекста.

`ThrowableColorResolver` разрешает итоговые цвета независимо от VS Code API и интерфейса настройки.

`ThrowableDecorationController` использует результат разрешения цветов при создании decorations. Некорректная эффективная
настройка сохраняет стандартную Java-подсветку соответствующего контекста без изменения конфигурации.

Сохранённые настройки изменяются через Settings и Settings JSON. Webview-панель предоставляет редактор черновика выбранной
области и просмотр эффективной сохранённой конфигурации.

`ThrowableColorSettingsPanel` управляет открытием, получением конфигурации, обновлением и завершением жизненного цикла
панели.

`ThrowableColorSettingsResources` определяет расположение ресурсов относительно `context.extensionUri`, загружает HTML-шаблоны
и проверяет доступность файлов стилей и скрипта.

`ThrowableColorSettingsViewModel` разделяет выбранную область, доступность `Workspace`, исходные значения и эффективную
конфигурацию.

`ThrowableColorSettingsViewModelBuilder` выбирает исходные значения области без подстановки эффективных значений. При
недоступности запрошенной `Workspace` используется `User`. Входной snapshot не изменяется.

`ThrowableColorSettingsHtml` получает шаблоны и модель представления и формирует итоговый HTML без обращения к файловой системе
и VS Code API.

HTML-шаблоны, CSS и `app.js` находятся в каталоге `webview/color-settings`. Стили и скрипт подключаются через `asWebviewUri`.
`localResourceRoots` ограничивает доступ каталогом панели.

Панель показывает значения черновика выбранной области `User` или `Workspace` отдельно от эффективной сохранённой
конфигурации. Строки, отсутствие настройки, явный `null` и пустая строка отображаются различимо.

Ошибка эффективной конфигурации не скрывает исходные значения. Эффективное сохранённое значение не подменяется вычисленным
цветом темы или результатом наследования.

Выбор области передаётся из `app.js` сообщением `selectTarget`. Расширение проверяет структуру сообщения и доступность области
через `ThrowableColorSettingsMessageParser`. Переключение обновляет представление и не записывает конфигурацию.

Повторный вызов команды использует существующую панель. Изменение конфигурации обновляет её содержимое.

После загрузки шаблонов панель получает актуальную конфигурацию. Результат не применяется к закрытой или заменённой панели.
Предыдущее обновление не заменяет содержимое более нового.

Ошибка актуальной загрузки отображается уведомлением. Устаревшие ошибки игнорируются. Повторный вызов команды позволяет
повторить загрузку.

Webview выполняет локальный скрипт `app.js`. Content Security Policy разрешает его выполнение с nonce, созданным расширением.
Сетевые ресурсы не загружаются. Значения настроек экранируются и не интерпретируются как HTML или дополнительные места
подстановки.

Скрипт управляет прокруткой таблицы и страницы. Анимация использует `requestAnimationFrame`; события колеса накапливают
целевую позицию одной анимации. Плавность и нативное поведение ввода проверяются в Extension Development Host.

Загрузка ресурсов, формирование HTML и асинхронный жизненный цикл панели покрыты автоматическими тестами.

Разделение представления реализовано согласно [ADR-0015](../decisions/0015-separate-vscode-color-settings-presentation.md).

CSS-переменные описаны в `web-types.json`. Подстановки HTML-шаблонов описаны в `tooling/template-variables.json`. Описания
ведутся на русском языке.

Каталог подстановок проверяется автоматическим тестом и не используется renderer. Метаданные не изменяют значения цветов,
правила подстановки и язык интерфейса панели.

`ThrowableColorSettingsPanel` хранит независимые черновики открытой панели для `User` и `Workspace`.
Перед формированием HTML значения выбранной области заменяются значениями её черновика.

`ThrowableColorSettingsDraft` сравнивает текущие значения полей с базовыми значениями области.
Возврат поля обновляет его базовое значение и сохраняет остальные изменения черновика.

Операции `setSource`, `setColor`, `resetField` и `revertField` обрабатываются отдельно.
`resetField` удаляет настройку из черновика. `revertField` получает актуальное сохранённое значение через configuration reader.

Запрос возврата содержит область, контекст и имя поля. Значение определяет расширение из конфигурации VS Code.

`ThrowableColorSettingsControlStateBuilder` вычисляет `canRevert` и `canRemove` по исходным значениям черновика
и сохранённому снимку той же области. Компонент не зависит от VS Code API и разметки.

Сравнение использует `Object.is` и не нормализует значения. Возврат доступен при различии значений.
Удаление доступно для значения, отличного от `undefined`.

Сохранённый снимок обновляется при чтении конфигурации для обновления панели и возврата поля.
Обычный ввод использует последний прочитанный снимок без повторного обращения к конфигурации.
Закрытие панели удаляет снимок вместе с черновиками.

`ThrowableColorSettingsDraftConfigurationBuilder` накладывает изменённые поля черновика на сохранённый снимок выбранной
области. Остальные поля снимка сохраняются.

Для предпросмотра значения объединяются отдельно по каждому ключу в порядке: значения по умолчанию, `User`, `Workspace`.
Только `undefined` обозначает отсутствие значения на уровне. Явный `null`, пустая строка и некорректные значения не пропускаются.

`ThrowableColorSettingsPreviewBuilder` использует `ThrowableColorResolver` и формирует результат `color`, `native`
или `invalid` для каждого контекста. Ошибка содержит причину и исходный контекст.

Наследующий контекст получает результат `CLASS`, включая стандартную Java-подсветку или ошибку.
Контексты с независимым источником сохраняют собственный результат. Вычисление не изменяет настройки и значения черновика.

Ответы `draftState` и `fieldReverted` передают состояния действий в поле `controls` и предпросмотр в поле `preview`.
Скрипт проверяет структуру обоих полей до изменения представления. Обновление выполняется без замены HTML.

При `inherit` и `native` поле цвета и связанные действия блокируются. Собственное значение черновика сохраняется
и восстанавливается при возврате к редактируемому источнику.

При переключении области элементы текущей таблицы отключаются до загрузки нового представления.
Сообщения состояния другой области не изменяют текущую таблицу.

Кнопки возврата и удаления первоначально отключены. После `ready` расширение передаёт состояния выбранной области.
Переключение области, отмена черновика и обновление конфигурации перестраивают представление.

Изменённый черновик сохраняется при обновлении конфигурации. Черновик без изменений перечитывается.
Отмена черновика загружает актуальные сохранённые значения выбранной области. Закрытие панели удаляет черновики обеих областей.

`ThrowableColorSettingsMessageParser` проверяет структуру сообщений, допустимые контексты, поля и доступность области.
Неполные строки цвета сохраняются в черновике без проверки завершённого HEX.

Проверки покрывают возврат актуального сохранённого значения, независимость областей, сохранение остальных изменений,
отклонение сообщений закрытой панели и отсутствие записи конфигурации при редактировании, возврате и отмене черновика.

Проверки расчёта состояний покрывают независимость полей и контекстов, отсутствие настройки, пустую строку, явный `null`,
некорректные значения и сравнение без нормализации.

Проверки панели покрывают состояния после ввода, удаления и возврата, различие областей и обновление сохранённого снимка.
Привязка действий и начальное отключение кнопок проверяются для обычных и ошибочных строк.
Синтаксис `app.js` проверяется как синтаксис классического браузерного скрипта.

Проверки построения конфигурации черновика покрывают независимое объединение источника и цвета, приоритет `Workspace`,
возврат к нижним уровням после удаления, явные `null` и пустые строки, ошибки разбора и неизменность входных данных.

Проверки предпросмотра покрывают наследование результата `CLASS`, независимые источники и ошибки отдельных контекстов.
Проверки панели подтверждают передачу предпросмотра без записи настроек и замены HTML.

Скрипт панели предоставляет текстовый ввод, нативный выбор RGB, ползунок `Opacity` и числовой ввод прозрачности.
Alpha хранится в строковом значении цвета. Отдельная настройка прозрачности не вводится.

Выбор RGB сохраняет текущий alpha. Ползунок использует точное значение байта от 0 до 255.

Числовой ввод прозрачности преобразует процент в ближайший байт alpha.
Enter и потеря фокуса нормализуют отображение по полученному значению.
Синхронизация контролов сохраняет введённый текст до завершения редактирования и не изменяет alpha.
Некорректный ввод не создаёт изменение цвета.

`parseHexColor` разбирает четыре формы HEX и предоставляет полный RGB и alpha для визуальных контролов.
Исходная строка сохраняется при синхронизации и выборе того же значения.

`updateColorControls` синхронизирует палитру, ползунок и поле процентов с текущим полем цвета.
Состояние контролов учитывает доступность редактирования, полный HEX и переключение области.

Ввод текста, выбор RGB и изменение alpha используют общий обработчик собственного цвета и сообщение `setColor`.
Повторное присваивание `value` при обычном текстовом вводе не выполняется.

Цветовой образец использует разобранный HEX предпросмотра. При стандартной Java-подсветке или ошибке образец скрывается.
Собственное значение и эффективный предпросмотр остаются отдельными данными.

`ThrowableColorSettingsWebview.test.ts` выполняет `app.js` в `node:vm`.
Проверки покрывают сообщения, значения и состояния контролов, все 256 значений alpha при выборе RGB и сохранение текста.

Модель DOM не выполняет браузерную отрисовку. Привязки элементов проверяются по HTML-шаблонам, визуальное поведение —
в Extension Development Host.

Применение изменений разделено между проверкой данных, записью конфигурации и управлением состоянием панели.

`ThrowableColorSettingsApplyValidator` проверяет изменения относительно актуальной конфигурации выбранной области.
При проверке `User` настройки `Workspace` не скрывают некорректное применяемое значение.

`ThrowableColorConfigurationWriter` последовательно записывает изменённые ключи в явно выбранную область.
Удаление передаётся как отсутствие значения. После первой ошибки запись останавливается.
Результат различает успешно записанные поля, неуспешное поле и оставшиеся изменения.

`ThrowableColorSettingsApplier` перечитывает конфигурацию перед проверкой и после записи.
Совпадающие значения пропускаются после проверки запроса.
Ошибки чтения до и после записи различаются; результат выполненных операций сохраняется.

После успешного применения черновик получает новое сохранённое состояние.
После частичной записи поверх актуальной конфигурации сохраняются неуспешные и ещё не записанные изменения.
При ошибке чтения текущий черновик сохраняется.

Панель блокирует редактирование и повторное применение на время операции.
Обновление представления откладывается до завершения записи.
Результат операции закрытой панели не изменяет состояние новой панели.

Webview учитывает неподтверждённые изменения отдельно от выбранного действия.

`requestAction` сохраняет действие и блокирует дальнейшее редактирование.
`dispatchPendingAction` отправляет его после получения всех подтверждений.

Пока ожидаются ответы, сохраняется текущая область. Это позволяет принять подтверждения перед её переключением.

Если подтверждённый черновик не содержит изменений, ожидающий `Apply` не отправляется.

Обычное редактирование черновика не заменяет HTML и не блокирует кнопки действий на время каждого ответа расширения.
Ожидание действий и переключение области покрыты автоматическими тестами webview.

Изменение конфигурации обновляет decoration controller без перезапуска Extension Development Host.

Ресурсы панели включают отдельные варианты иконки вкладки для светлой и тёмной темы.

Команда открытия панели подключена к `extension/context` с условием по идентификатору расширения.
Для проверки меню используется локальная установка прототипа из папки.

Реализация выполняет часть [ADR-0014](../decisions/0014-interactive-vscode-color-settings.md). Интерактивная настройка
остаётся обязательной итерацией перед первым публичным выпуском VS Code.

## Известные ограничения

Прототип не подтверждает полное соответствие контракту Java-подсветки.

Разрешение ссылок зависит от готовности Java-поддержки и доступности определений. До подтверждения типа сохраняется
стандартная Java-подсветка.

Каталог известных типов ограничен. Для остальных классов требуется доступная цепочка наследования до подтверждённого типа
из каталога.

Синтаксический разбор объявлений и контекстов не является полным синтаксическим разрешением Java-кода.
